We know Claude co-authored this commit. We don't know which lines, from what prompt, or what the human changed after. The "Co-Authored-By" tag is a confession without details. SonarQube sees it and runs the same checks. Snyk sees it and runs the same checks. The reviewer sees it and still can't tell which lines reflect human reasoning and which are model output. Every tool has the binary signal — "AI was here" — but none can act on it.

The Trust Gap

Credit where it's due: we're not starting from zero. Claude Code adds "Co-Authored-By" tags. GitHub flags Copilot suggestions. The industry has acknowledged that AI is in the authorship loop. The problem isn't awareness. It's granularity.

Today's tools — SonarQube, Snyk, CodeQL, your test suites, your code review process — are genuinely sophisticated. They catch real bugs, real vulnerabilities, real quality issues. Some of them can even see the co-author tag. But knowing "AI was involved" and knowing "these specific lines came from Claude 4, prompted with this intent, and the human modified the error handling" are fundamentally different levels of information. The first is a flag. The second is actionable provenance.

This granularity matters because AI-generated code fails differently than human-written code. That's not a theoretical claim. The failure patterns are concretely different — and your current toolchain is optimized for one set while being largely blind to the other. Don't take our word for it. Try to spot the bugs yourself.

Human-Written Authentication check
function verifyToken(token) { try { const decoded = jwt.verify(token, SECRET); return { valid: true, user: decoded }; } catch (err) { return { valid: false }; } }
Human Bug: Missing expiration check
The developer forgot to check decoded.exp against the current time. An expired token still returns valid: true. Classic human oversight — they know JWT but forgot one check under time pressure.

AI-Generated Authentication check
function verifyToken(token) { try { const decoded = jwt.verify(token, SECRET); if (decoded.exp < Date.now()) { return { valid: false, reason: 'expired' }; } if (!decoded.permissions.includes('read')) { return { valid: false, reason: 'insufficient' }; } return { valid: true, user: decoded }; } catch (err) { return { valid: false, reason: err.message }; } }
AI Bug: Hallucinated schema assumption
The AI assumed the JWT payload has a permissions array because most training examples did. Your tokens use roles, not permissions. The code is structurally perfect — expiry check, permission check, error handling — but decoded.permissions is undefined, so .includes() throws. Every token fails in production.

Human-Written Data encryption
function encrypt(data, key) { const iv = crypto.randomBytes(16); const cipher = crypto.createCipheriv( 'aes-256-cbc', key, iv ); let encrypted = cipher.update(data, 'utf8', 'hex'); encrypted += cipher.final('hex'); return iv.toString('hex') + ':' + encrypted; }
Human Bug: CBC instead of GCM
The developer used AES-256-CBC, which provides confidentiality but not integrity. An attacker can modify the ciphertext without detection (padding oracle attack). Should use AES-256-GCM which includes authentication. A common mistake from following older tutorials.
CodeQL ✓ Semgrep ✓ Code Review ✓ Tests ✗
AI-Generated Data encryption
function encrypt(data, key) { const iv = crypto.randomBytes(12); const cipher = crypto.createCipheriv( 'aes-256-gcm', key, iv ); let encrypted = cipher.update(data, 'utf8', 'hex'); encrypted += cipher.final('hex'); const tag = cipher.getAuthTag(); return iv.toString('hex') + ':' + encrypted + ':' + tag.toString('hex'); } function decrypt(payload, key) { const [ivHex, encHex, tagHex] = payload.split(':'); const decipher = crypto.createDecipheriv( 'aes-256-gcm', key, Buffer.from(ivHex, 'hex') ); decipher.setAuthTag(Buffer.from(tagHex, 'hex')); let decrypted = decipher.update(encHex, 'hex', 'utf8'); decrypted += decipher.final('utf8'); return decrypted; }
AI Bug: Auth tag set before ciphertext
The AI correctly chose GCM, generated a proper auth tag, and the code looks textbook-perfect. But setAuthTag() is called before decipher.update() — in some Node.js versions, the auth tag must be set after feeding all ciphertext but before final(). The code works in Node 16 but silently fails authentication in Node 20+. The AI pattern-matched from training data that spanned multiple Node versions.
CodeQL ✗ Semgrep ✗ Snyk ✗ Code Review ✗* Tests ✓**
* Even a senior reviewer would likely approve this — the code looks correct. ** Only if running tests on the actual target Node version.
Human-Written Database query
async function getActiveUsers(orgId) { const users = await db.query( `SELECT * FROM users WHERE org_id = ${orgId} AND status = 'active'` ); return users.rows; }
Human Bug: SQL injection
Classic SQL injection via string interpolation instead of parameterized query. Every security tool in existence catches this. It's the poster child of human security mistakes — the developer knew better but took a shortcut.
CodeQL ✓ Semgrep ✓ SonarQube ✓ ESLint ✓ Code Review ✓
AI-Generated Database query
async function getActiveUsers(orgId) { const users = await db.query( 'SELECT id, name, email, role FROM users ' + 'WHERE org_id = $1 AND status = $2', [orgId, 'active'] ); return users.rows.map(u => ({ ...u, isAdmin: u.role === 'admin' })); }
AI Bug: Assumed schema, exposed role data
The AI wrote a perfectly secure parameterized query. But it assumed role is a column on the users table (your schema stores roles in a separate junction table). The query returns null for u.role, so isAdmin is always false — silently breaking admin access. Also, by selecting and returning role data to the client, it exposes authorization info that should stay server-side. The query is safe. The data model assumption is wrong.
CodeQL ✗ SonarQube ✗ Snyk ✗ Tests ✓* Code Review ✗**
* Only if integration tests check actual admin behavior. ** Reviewer would need deep schema knowledge to catch this.

The pattern is clear: human bugs are structurally visible — wrong syntax, missing checks, known anti-patterns. AI bugs are semantically invisible — correct syntax, plausible structure, wrong assumptions about your specific system. Your current tools are brilliant at the first category and nearly blind to the second.

The authorship model is evolving through three phases — from a binary co-author flag, to line-level provenance, to a full provenance tree. In each phase, the trust infrastructure adapts to the granularity available — and gains the ability to target verification where AI-generated code actually needs it. Below is a working model. What's Actually Changing

The shift from identity-based trust to provenance-based trust isn't just a technical upgrade. It changes what we verify, how we verify it, and why.

In 2026, authorship is a name and a flag. Git blame shows sarah_dev. The commit says "Co-Authored-By: Claude." We've acknowledged the AI — that's progress. But the flag is binary and commit-level. It doesn't tell the security scanner which three lines to check for hallucinated API calls. It doesn't tell the reviewer which function was entirely model-generated versus which one the human wrote from scratch. The gap isn't awareness. It's actionable granularity.

In 2028, authorship is a chain. The system records: sarah_dev prompted Claude 5 to implement rate limiting using token bucket pattern, then reviewed and modified the output. Now the reviewer can assess intent-to-output alignment. The security scanner applies AI-specific checks to the generated portions. The test generator creates additional edge cases targeting known AI hallucination patterns. Trust becomes informed.

In 2032, authorship is a tree. An orchestrator decomposed the feature request into sub-tasks. A code agent, a test agent, and a security agent each contributed. Every contribution carries provenance: which agent, which constraints, which model version, what evidence supports it. Trust isn't in any single actor. It's in the completeness and integrity of the provenance chain — and whether the evidence gathered is proportional to the risk.

Binary flag ("AI was here") → Granular metadata (which lines, what prompt, which model)
Same checks for all code → AI-origin-aware verification
Trust the author's identity → Trust the evidence chain
Independent tool signals → Correlated, risk-proportional profile

The Trust Model Must Evolve

The question is no longer "who wrote this code?" It's "is the evidence sufficient for the risk?" When we stop treating authorship as identity and start treating it as provenance, we build trust models that are honest about how code is actually produced — and rigorous about how it's actually verified.

The organizations that navigate this transition well won't be the ones that ban AI tools or the ones that adopt them blindly. They'll be the ones that rebuild their trust infrastructure to match the new authorship reality — declaring AI provenance, adapting verification to origin, and measuring evidence sufficiency against risk.

You've just operated inside that transition. The blind spot in 2026 is real — it exists in your codebase right now. The question is whether you close it deliberately or wait until a failure forces you to.
